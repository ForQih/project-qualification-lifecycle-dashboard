Quick Reference Guide

GAMP 5 Software Categories (1, 3, 4, 5)

GAMP 5 scales validation effort based on software complexity and risk—so simple tools don't require the same heavy documentation as custom-built apps.

Cat 1 — Infrastructure Software Lowest Effort

Layered OS, databases, networks, and backup tools supporting apps. Focuses on IQ/OQ verification; skips FS/DS, DQ, and PQ.

Examples: Windows/Linux OS, Oracle/PostgreSQL DB, VMware, Antivirus.
Cat 3 — Non-Configured Products Low–Medium

Commercial off-the-shelf software used "as-is" without customizing business workflows. Skips VP, FS/DS, DQ, Supplier Assessment & PQ.

Examples: Standalone lab balance software, standard PDF tools, simple COTS utilities.
Cat 4 — Configured Products High Effort

Commercial software configured to match plant workflows without changing core source code. Requires all deliverables except Source Code Review.

Examples: ERP (Oracle/SAP), LIMS, eQMS, SCADA, Commercial CMMS.
Cat 5 — Custom Applications Full Validation

Bespoke applications coded from scratch by internal IT or a vendor. Highest risk—requires every qualification deliverable including Source Code Review.

Examples: In-house web apps, custom middleware/APIs, custom MES scripts.
Where is Category 2? Category 2 (Firmware) was officially retired in GAMP 5 and merged into Cat 3, 4, or 5 based on complexity. Global pharma standards intentionally kept the numbering 1, 3, 4, 5 for historical continuity.
IT & CSV Practical Guideline (GAMP 5 & ISO 27001)

Zero-Redundancy Backup & Restore Strategy

Core Regulatory Objective (CPOB Annex 11 Sec 7.2 • 21 CFR 11.10(c) • ISO 27001 A.8.13)
Guarantee that GxP Data & Audit Trails cannot be lost or corrupted and can be recovered 100% intact (ALCOA+) within business-agreed RPO & RTO targets. Under GAMP 5 Critical Thinking, do not repeat identical restore tests across IQ, OQ, and PQ.
1. Database vs. Application (Win-Win IT & CSV Split)
Backup Database Mandatory Daily

Automated scheduled DB dump (encrypted + offsite/DR copy) because GxP transactions & Audit Trails grow continuously.

Restore Database Test 1× in OQ

Executed once in Staging (Server Q) during OQ. Proves 100% data & Audit Trail recovery within RTO with zero risk to Production.

Backup Application Git Tag / Snapshot

Application binaries are static between Change Controls. Controlled Git release tags (e.g., v1.0.0) + config/VM snapshot satisfy app backup.

Restore Application Leverage IQ / VM

Do not manually rebuild apps from scratch during OQ/PQ. Git deployment during IQ already proves app rebuild; use VM Snapshots at infra level for DR.

2. Where It Happens & Required Evidence (Zero Duplication)
URS & FDS
Define & Design: URS states Retention (e.g., 10 yrs), RPO & RTO. FDS defines DB cron schedule, encryption, offsite vault, Git repo & restore runbook.
IQ (Stg & Prod)
Config Check ONLY (No Restore Test): Verify backup job active, first DB dump > 0 KB created, and Git tag deploy log (proves app installation/rebuild).
OQ (Staging)
EXECUTE 1× FULL DB RESTORE TEST: (1) Screenshot dummy data + Audit Trail → (2) Trigger DB backup → (3) Delete/corrupt Staging DB → (4) Execute DB restore & log RTO duration → (5) Verify 100% data & Audit Trail intact.
PQ (Prod)
DO NOT REPEAT: Leverage OQ Staging pass result + IQ Prod backup config. Never run destructive restore tests against Production DB (ISO 27001 A.8.31).
3. Post Go-Live: SOP & Periodic Review (Multi-App Portfolio)

For ongoing Production proof, use Cross-Environment Restore (Prod DB Backup → Restore into Isolated Staging/DR Sandbox). Because IT manages many apps, IT & CSV should agree on a Risk-Based Periodic Restore Schedule inside the Periodic Review SOP:

  • Critical / High-Risk Apps (ERP, LIMS, ePM, eQMS): 1× annual DB restore drill into isolated Staging/DR.
  • Medium / Low-Risk Apps: Rotating cluster sampling (e.g., 1–2 representative apps per shared DB server/year) when backup methods are identical.
